# Правила работы над ДАР-Скрин

## Сначала прочитай
Перед любым изменением кода или документации прочитай ABOUT.md, этот файл и актуальные документы в docs/. Не придумывай требования, которых нет в документации. Неподтверждённые допущения помечай явно и не превращай их в уже согласованные факты.

Не создавай AGENTS.md и не дублируй эти правила в других файлах. Источники: ABOUT.md (что за проект) и AGENT.md (как работать).

## Продукт
Это сервис назначения и заполнения анкет, а не медицинский эксперт. Запрещено реализовывать интерпретацию, балльные медицинские выводы и рекомендации врача, пока нет утверждённой методики и отдельной задачи.

Официальные формулировки вопросов и вариантов ответа не выдумывать и не «улучшать». В разработке допустим явно помеченный демонстрационный минимальный шаблон, который не подменяет официальную анкету.

На тестовой ВМ использовать только синтетические данные. Не переносить реальные персональные или медицинские сведения.

Интерфейс — на русском. Кнопки называют действие: «Отправить анкету», а не «ОК». Пустые разделы «Медосмотр» и «Отчёты» не показывать.

## Архитектура и границы MVP
Держим один модульный монолит. В рамках MVP не добавлять React, микросервисы, Redis, Celery, Django REST Framework и реальное API. Общую бизнес-логику писать в сервисном слое, а не только внутри views, чтобы позже к ней можно было подключить /api/v1/.

События assigned, submitted, returned, reviewed можно фиксировать через простой программный интерфейс без брокера, очереди и outbox. Уведомления в мессенджеры и планировщик напоминаний о сроке не реализовывать.

Не строить универсальный конструктор любых форм. Достаточно модели шаблона, версии, пунктов, типов ответа и условий показа.

Контейнер обследования должен допускать поздние разделы (медосмотр, итог), но не проектируй их сверх необходимой точки расширения.

## Данные и безопасность
Секреты только в переменных окружения. В репозитории — .env.example без значений. Не печатать пароли, ответы анкет и медицинские данные в логах, коммитах и localStorage.

Права проверять на сервере, на уровне объекта, для каждого назначения. Сессии Django и CSRF обязательны с начала реализации — не откладывать до выхода из тестового контура. Администратор по умолчанию не должен получить ответы даже по прямой URL. Сотрудник видит только своё. После деактивации пользователя сессии сбрасываются, история сохраняется.

Автосохранение подтверждается сервером или показывает ошибку. Защитить гонки автосохранения и отправки: после отправки черновые сохранения не должны портить отправленный снимок.

Переходы статусов только из допустимого списка, проверка на сервере. Просрочка — вычисляемый признак, не статус.

Опубликованную версию шаблона не изменять; правки — через копию. Назначение хранит неизменяемую ссылку на версию шаблона.

Не удалять и не переписывать уже применённые миграции. Для рискованных изменений иметь план отката.

Не включать в обычные инструкции команду docker compose down -v: она уничтожает тома с данными.

Не раскрывать PostgreSQL наружу. Не использовать django runserver как способ внешнего доступа на ВМ. Для доступа снаружи — Gunicorn за обратным прокси. HTMX и статика — локально, без CDN. Ограничение попыток входа и TLS — до применения вне тестового контура (CSRF, сессии и объектные права уже обязательны с начала реализации).

Резервное копирование делает сервер, не приложение. В docs/deployment.md описать, что сохранять: PostgreSQL, загруженные файлы (если появятся), конфигурацию и секреты.

## Как работать в Cursor
Пользователь переносит задания и отчёты между чатами. Чаты сами друг друга не вызывают.

Один чат — дирижёр: ставит задачу, принимает отчёт, после тестов объединяет изменения, обновляет docs/plan.md. Обычно не больше двух рабочих задач одновременно.

Если есть git и настроены worktree — одна ветка или worktree на задачу, не работать вдвоём в одной общей папке. Если worktree не настроены — работать последовательно.

Модели, миграции, зависимости, Docker Compose и общие базовые шаблоны принадлежат одному исполнителю в один момент времени. Интерфейсы (URL, имена, контракт сервисов, контекст шаблонов, статусы) фиксируются до параллельной вёрстки. Не назначать двум чатам одни и те же конфликтные файлы.

Сначала осмотри существующие файлы. Не перезаписывай чужую работу без явной необходимости. Не выполняй разрушительные команды «на всякий случай».

Не выбирай версии зависимостей «самые новые наугад». Бери совместимые поддерживаемые версии и фиксируй их в файлах зависимостей на этапе реализации.

Новое поведение покрывай тестами. Не объявляй этап готовым без фактических команд и их результатов.
