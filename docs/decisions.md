# Решения и допущения

## Подтверждённые решения

- Продукт: назначение и заполнение анкет для обследования работников одной организации; один терапевт на всех в первой версии.
- Не реализовывать медицинскую интерпретацию, балльные выводы и системные «рекомендованные заключения».
- Официальные формулировки анкет не выдумывать и не править; до реального применения подтвердить расшифровку бланков. В разработке допустим явно демонстрационный минимальный шаблон.
- Две возрастные формы; возраст — полные годы на дату назначения по дате рождения в карточке; в день 65 лет — форма 65+; версия шаблона в назначении неизменна.
- Несколько параллельных назначений одному человеку разрешены.
- Типы пунктов: да/нет, число, текст, один вариант; условия показа в БД; пустой ответ ≠ «нет».
- Базовые статусы жизненного цикла (`assigned`, `draft`, `submitted`, `returned`, `reviewed`, `canceled`) и согласованные переходы заполнения/проверки — в [workflow.md](workflow.md); просрочка вычисляемая (не статус). Детали отмены и нового срока при возврате — в допущениях ниже.
- После `submitted` — чтение; правка только в `returned` (любые пункты); после `reviewed` — без правок; снимки отправок неизменяемы.
- При возврате комментарий врача обязателен и виден сотруднику.
- Изменение срока фиксируется в аудите (кто, когда, старое/новое значение, назначение).
- Администратор по умолчанию без доступа к ответам, в том числе по прямой URL.
- С начала реализации: сессии Django, CSRF, серверные проверки прав на каждое назначение. Не откладывать до выхода из тестового контура.
- Стек MVP: Python, Django, PostgreSQL, шаблоны Django, HTMX, Docker Compose; один модульный монолит; тесты только на PostgreSQL.
- Вне MVP: React, микросервисы, Redis, Celery, DRF/API, боты, уведомления, конструктор, импорт сотрудников, резерв в UI.
- Модули: accounts, directory, questionnaires, screenings; сервисный слой; простой интерфейс событий без брокера; задел `/api/v1/` без реализации.
- Дизайн вариант 1: светлый UI, изумрудные акценты, компактная боковая панель; русский интерфейс; без пустых будущих разделов.
- Секреты не в репозитории; PostgreSQL не снаружи; без runserver снаружи; локальный HTMX; в обычном runbook нет `docker compose down -v`.
- Имя файла правил: `AGENT.md` (не создавать `AGENTS.md`).

## Рекомендуемые допущения

Не подтверждены заказчиком как жёсткое ТЗ; помечены явно. Не выдавать за согласованные факты без отдельного решения.

1. **Вход:** локальный логин и одноразовый пароль; обязательная смена при первом входе; администратор передаёт учётные данные вне сервиса. Значения секретов в репозиторий не писать.
2. **Часовой пояс:** предлагаемый `TIME_ZONE=Asia/Barnaul` до подтверждения; все календарные сравнения дат — в этом поясе.
3. **Срок и просрочка:** день указанного срока включителен; просрочка начинается на следующий календарный день после даты срока (и только для статусов `assigned` / `draft` / `returned`).
4. **Новый срок при возврате:** терапевт обязан указать новый срок (может явно оставить ту же дату). Само наличие обязательного комментария при возврате — подтверждено (см. выше).
5. **Отмена:** разрешена до статуса `reviewed` (из `assigned` / `draft` / `submitted` / `returned`), с аудитом, без жёсткого удаления записей.
6. **Изменение срока — допустимые статусы (предложение):** разрешить в `assigned`, `draft`, `returned`; не разрешать в `reviewed` и `canceled`; для `submitted` — уточнить отдельно. Не считать согласованным ТЗ.
