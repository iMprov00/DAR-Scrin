# Развёртывание (тестовая ВМ)

## Целевая среда

- Linux-ВМ для теста.
- Docker Compose: сервисы `db` (PostgreSQL 16), `app` (Django + Gunicorn), `nginx` (обратный прокси).
- Снаружи: nginx на порту хоста **8080** → Gunicorn внутри сети Compose (`app:8000`).
- Порт PostgreSQL **не** открывать наружу (у сервиса `db` нет `ports` на хост).
- `django runserver` **не** использовать как способ внешнего доступа на ВМ.
- HTMX и статика — **локально** (`/static/vendor/htmx.min.js`), без CDN.
- Только **синтетические** данные. Реальные персональные/медицинские сведения не переносить.
- Часовой пояс приложения: `TIME_ZONE=Asia/Barnaul` (в настройках Django).

## Конфигурация и секреты

- Секреты только в переменных окружения файла `.env` на ВМ.
- В репозитории — [`.env.example`](../.env.example) **без значений**. Файл `.env` в git не коммитить.
- С начала реализации: сессии Django, CSRF, серверные проверки прав на каждое назначение.
- **До боевого применения (сейчас не внедряем):** TLS на прокси; ограничение попыток входа (троттлинг).

## Runbook (конкретные команды, без уничтожения данных)

Рабочий каталог — корень репозитория на ВМ.

### 1. Окружение

```bash
cp .env.example .env
# заполнить DJANGO_* и POSTGRES_* на ВМ; не коммитить .env
```

### 2. Поднять или обновить стек

```bash
docker compose up -d --build
docker compose ps
```

Тома: `postgres_data` (БД), `static_volume` (статика для nginx). **Не** использовать `docker compose down -v`.

### 3. Миграции и статика

Выполняются автоматически в [`scripts/entrypoint.sh`](../scripts/entrypoint.sh) при старте `app`:

- ожидание готовности PostgreSQL;
- `python manage.py migrate --noinput`;
- `python manage.py collectstatic --noinput`;
- запуск Gunicorn на `0.0.0.0:8000`.

Отдельный ручной `migrate` / `collectstatic` в обычном runbook не требуется.

### 4. Синтетические демо-данные

```bash
docker compose exec app python manage.py load_demo_questionnaire
docker compose exec app python manage.py createsuperuser
```

Сотрудник и терапевт: Django Admin — флаги ролей, профиль сотрудника (организация, подразделение, дата рождения). Только синтетика; пароли и ответы анкет не писать в логи, коммиты и отчёты.

### 5. Проверки после подъёма

```bash
# вход через nginx
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/login/

# локальный HTMX (ожидается 200)
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/static/vendor/htmx.min.js

# PostgreSQL не проброшен на хост (ожидается {})
docker compose ps
docker inspect "$(docker compose ps -q db)" --format '{{json .HostConfig.PortBindings}}'
```

В браузере: `http://<хост>:8080/login/`.

### 6. Перезапуск без потери данных

```bash
docker compose restart
# или:
docker compose down          # без -v
docker compose up -d
```

После рестарта данные в PostgreSQL сохраняются, пока не удалены тома.

**Запрещено в обычных инструкциях:** `docker compose down -v` — уничтожает тома с данными.

## Сохранность данных

После `restart` или `down` + `up -d` **без** `-v` должны сохраняться:

- данные PostgreSQL в томе `postgres_data`;
- собранная статика в `static_volume`;
- загруженные файлы приложения, если появятся позже (пока отдельного media-тома нет).

Проверка: создать маркерную запись (например, синтетический username) → перезапустить стек без `-v` → запись на месте; `docker volume ls` показывает `*_postgres_data` и `*_static_volume`.

## Резервное копирование

Резерв делает **сервер / администрирование ВМ**, не приложение. Интерфейса резервного копирования в MVP нет.

Что сохранять на стороне сервера:

| Объект | Зачем |
|--------|--------|
| Том или логический дамп PostgreSQL (`postgres_data` / `pg_dump`) | данные назначений, учёток, шаблонов |
| Загруженные файлы | если появятся (media); сейчас могут отсутствовать |
| Конфигурация | `docker-compose.yml`, `nginx/default.conf`, версия/тег образа `app` |
| Секреты | файл `.env` и иные секреты ВМ **вне git**, по процедуре сервера |

## Краткий план отката

1. Остановить выкладку новой версии приложения; **тома и БД не удалять**.
2. Вернуть предыдущий образ / тег сервиса `app` в Compose (или checkout предыдущего коммита + `up -d --build` без `-v`).
3. Поднять стек: `docker compose up -d` **без** `-v`.
4. Если миграции новой версии уже применены и несовместимы со старым кодом — восстановить БД из **резервной копии сервера** (или выполнить заранее проверенный обратный путь миграций). Не использовать очистку томов как «откат».
5. Проверить `http://<хост>:8080/login/` и ключевой сценарий на синтетике.
6. Не применять `docker compose down -v` как способ отката.

## Боевое применение

До использования вне теста: подтверждённые бланки анкет, **TLS**, **троттлинг попыток входа**, усиленная конфигурация безопасности, отработанная процедура резерва и восстановления на стороне сервера. В тестовом контуре эти пункты **не обязательны к внедрению**.
